# Self Hosting

This repository is used to store information about the services I self-host.
I have some Raspberry Pi's that are responsible for all self-hosted services.
The goal is to reclaim my privacy by owning my own data and using simple hardware to do so.

In the `/docs` folder I also keep some documentation about several things I needed to do.

## Services

These services are currently part of the setup:

- `Portainer` to manage the Docker containers
- Monitoring services
  - `Netdata` to scrape current system metrics
  - `Prometheus` to store the metrics in a database
  - `Grafana` to visualize the metrics
- `Caddy` to create a local reverse proxy
- `Samba` to provide a network share
- `Navidrome` to stream my music collection
- `Baikal` to host my calendar and contacts (CalDAV & CardDAV)
- `Donetick` to track household chores
- `Vaultwarden` to manage accounts and passwords

## First setup

### Setup the server and run the containers

1. Install Docker and Docker Compose on the server (see [pi-docker.md](./docs/pi-docker.md))
2. Encrypt and mount the HDDs on the server (see [pi-hdd.md](./docs/pi-hdd.md))
3. BACKUP THE LUKS HEADERS! (see [pi-hdd.md](./docs/pi-hdd.md))
4. Make sure all settings are set (don't forget the samba users and donetick secret)
5. Move the `.env`, `docker-compose.yml` and `prometheus.yml` file to the server
6. Create the `/mnt/data/samba` and `mnt/data/donetick/config` directories
7. Move the `/samba/smb.conf` and `/samba/users.conf` file to the server at `/mnt/data/samba`
8. Move the `/donetick/selfhosted.yml` file to the server at `/mnt/data/donetick/config`
9. Run `docker-compose up -d`

To make sure everyone in the `smb` group can read and write to the samba share, you need to make sure that the `/mnt/data/samba/share` folder is owned by the `smb` group. To do this run:

```shell
sudo chgrp -R 1000 /mnt/data/samba/share
sudo chmod -R g+w /mnt/data/samba/share
# ensure new files inherit group
sudo chmod g+s /mnt/data/samba/share
```

### Setup your devices

On the devices that need access to the server you need to make sure the DNS for `home.huizehop` resolves to the right IP address.

For Windows edit the `C:\Windows\System32\drivers\etc\hosts` file, add the following line:

```text
192.168.68.66  home.huizehop
```

In order to use Vaultwarden you need to trust the certificate generated by Caddy.
First copy the certificate to your user folder on Linux.

```shell
cp /mnt/data/caddy/data/caddy/pki/authorities/local/root.crt ~/caddy-ca.crt
```

Then move this file to your local machine (using FileZilla for example).
On Windows double click the certificate and click `Install Certificate`.
Choose `Local Machine`, then `Place all certificates in the following store`, `Browse` and select `Trusted Root Certification Authorities`.
Then click `OK`.

Finally make sure to remove the certificate from your root folder again.

```shell
rm ~/caddy-ca.crt
```

### Setup local backup

I backup the important files to the second HDD using `rsync`.
These steps are described in [pi-hdd.md](./docs/pi-hdd.md), but I'll repeat them here.
To set this up open the `crontab` file:

```shell
sudo crontab -e
```

Then add the following line:

```text
0 3 * * * rsync -a --delete /mnt/data/ /mnt/backup
```

This will synchronize both HDDs everyday at 3:00.
Important to note is that the `--delete` parameter will delete files from `/mnt/backup` that are no longer in `/mnt/data`.
I might change this in the future so only certain directories are synchronized.
There is probably no reason to backup the Netdata directory for instance.

### Setup remote backup

In addition to the local backup, the data is backed up off-site to Scaleway
Object Storage using `restic`.
This protects against scenarios where both local HDDs are lost at once (theft, fire).
The steps are described in [pi-backup-scaleway.md](./docs/pi-backup-scaleway.md).

### Troubleshooting

I have seen some instances where, after the containers all started, some services did not start.
In the logs I found that there were some `permission denied` errors.
To fix those I had to run these commands again:

```shell
# Shut down the containers
docker-compose down

# Change the permissions
sudo chown -R USERNAME:USERNAME /mnt/data/<specific-service>

# Start the containers again
docker-compose up -d
```

This makes the user that runs the docker compose file the owner of the directory in `/mnt/data`.
Don't run this on the entire directory, as the Baikal service requires the Nginx user as owner.
